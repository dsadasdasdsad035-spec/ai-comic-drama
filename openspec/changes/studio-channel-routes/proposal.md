# Proposal

## Why

设置页「连接与模型」里配置了 8 个渠道、347 个模型，但创意会话的模型选择器只呈现一个名为 `storyboard` 的无名分组，200 个条目全部是 `sb/<模型键>` 技术 id：用户看不到渠道归属，也看不到自己起的中文显示名。同一次投影还丢掉了默认模型的来源判定 —— `dsh/studio-default.json` 一旦缺失，默认模型就永久冻结在旧值上，设置页改了「创意（对话助手）」绑定也不生效。

这两件事同源：应用把「模型是什么」投影给宿主时只写了 id，其余事实（渠道、显示名）全部丢弃，默认模型又只看模型不看渠道。要修的是投影契约，不是补几个字段。

## What Changes

- 宿主的模型提供者从「一个 `storyboard` 大组」改为「按应用渠道拆成多个路由」：路由 id 形如 `sb-<渠道 id>`，路由显示名沿用设置页的渠道 label，`baseURL` 全部指向应用自身的 OpenAI 兼容门面（账本路径不变）。
- 模型条目写入应用侧的显示名（`name`），视觉能力仍以 `input: [text, image]` 表达。
- 路由归属显式化：应用记录自己写过哪些路由（`studio-routes.json`），只增删改自己拥有的路由，宿主或用户在 patch 里另加的 provider 原样保留；渠道被删除或不再有可用文本模型时，对应路由随之退场。
- **BREAKING**：旧 `storyboard` 路由退场。`agent-default-model` 中记录的 `provider: storyboard` 被一次性改写为模型所属渠道的 route；在会话里手动选过 `storyboard/<模型>` 的历史会话下次需重新选一次模型（选择器会退回「选择模型」）。
- 默认模型改为「路由 + 模型」配对校验：值必须与模型所属渠道一致；来源判定引入「用户显式选择」封存态，避免来源记录缺失时永久冻结，也避免覆盖用户在宿主里自己选的模型。
- 可用文本模型为空时写入一条专用兜底路由与占位模型，保持「绝不回落到宿主内置官方路由」的既有性质。
- 配置同步的变更签名纳入路由、显示名与默认配对，保证设置页保存后热生效，不必重启宿主。

## Capabilities

### New Capabilities

（无新增能力：本次是既有投影契约的修正，不引入新的系统行为边界。）

### Modified Capabilities

- `creative-dsh-host`: 「创意模型调用必须经过应用代理与账本」这一要求补充模型目录的投影形态 —— 宿主模型选择器 MUST 按应用渠道分组、MUST 显示应用侧显示名、每条路由 MUST 经应用门面；默认模型 MUST 始终指向本次同步写入的路由，MUST NOT 悬空到已退场的路由。
- `creative-chat`: 「创意会话模型由宿主设置解析」这一要求补充两层约束 —— 三层解析得到的默认模型 MUST 落到其所属渠道的宿主路由；模型选择器呈现的条目 MUST 使用应用侧的模型显示名与渠道显示名。

## Impact

受影响代码：

- `server/app.ts`：新增按渠道分组的模型投影（模型侧现成的 `listStudioModels()` 保留给门面）。
- `server/studio-profile.mjs`：写入多路由、路由归属清理、默认模型配对判定与迁移、兜底路由。
- `server/index.mjs`：变更签名扩充、同步日志摘要。
- `tests/studio-model-routing.mjs`：现有默认模型用例改为渠道路由语义，新增分组、显示名、清理、迁移、兜底、显式选择保留等用例。
- `docs/creative-host.md`：补「模型投影：按渠道分路由」一节与宿主侧热生效边界。

不受影响：

- `server/openai-gateway.mjs` 与 `/v1/*` 契约：模型 id 仍为 `sb/<模型键>`，门面无需改动。
- 账本、预扣、结算、输出上限截断：路由只改宿主的配置形态，不改请求出口。
- 宿主（`deepseek-harness`）源码：分批路由是宿主原生支持的多 provider 形态，无需改动或打补丁。

已知边界（写入文档，不在本次解决）：渠道 label 与宿主内置官方 provider 同名时（例如应用里的「DeepSeek」渠道与内建 `deepseek-official`），两者会各占一个分组；未给内置 provider 配 Key 时它不出分组，因此当前不可见。目录同步产生的超长分组（单渠道 186 个模型）属于「模型数量」问题，与本次「归属可见」问题分开评估。
