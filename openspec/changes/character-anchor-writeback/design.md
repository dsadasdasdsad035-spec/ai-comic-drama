# Design

## Context

角色数据同时存在两种形状：

- 接口 / 存储形状（蛇形）：`look_cn`、`look_en`、`expression_sheet`、`reference_images`、`voice`……服务端 `characters` 表与 `GET /api/project` 都只认这一种。
- 界面模型（驼峰）：`CharacterSheet`，`lookCn`、`lookEn`、`expressionSheet`、`referenceImages`、`voiceId`……

转换器 `toSheet` / `toProject`（`src/charMap.ts`）本来承担了这层映射，但只在部分路径上被使用。创意会话（`CreativeStudio`）不注入 `getSnapshot`/`setSnapshot`，因此助手工具拿到的项目快照**始终**是 `getProject` 返回的接口形状；`draftCtx` 里显式传入的 `project` 同样是接口形状。也就是说，所有把 `project.characters` 直接当 `CharacterSheet[]` 用的地方，读到的锚点、参考图、音色字段都是 `undefined`。

服务端 `saveProject` 对 `characters` 是「整表删除后按提交内容重建」，因此写入端任何一个字段漏掉都会直接表现为数据被清空，不会保留旧值。

约束：不改服务端契约；不在浏览器端引入新的状态管理层；存量项目不能因为修复而重排或丢失其它字段。

## Goals / Non-Goals

**Goals:**

- 让「读项目角色」「写项目角色」各自只有一个入口，消除散落的形状假设。
- 让合并阶段保留的锚点必定出现在写入内容里，并可被后续读取原样取回。
- 让同一类断层在提示词锚点展开、角色参考图、角色音色三个已知消费点上一起消失。

**Non-Goals:**

- 不重写 `CharacterSheet` / `ProjectChar` 的字段集合，不新增角色字段。
- 不改服务端 `characters` 表结构与 `saveProject` 的整表重建语义。
- 不做存量锚点回填：项目 `a` 的三个角色在库内没有对应提交记录，没有可信来源可回填。
- 不改角色参考图、三视图既有生成流程，只改它们读取角色数据的方式。

## Decisions

### 决策 1：读入口统一为 `readCharacters(project)`，而不是逐处补 `toSheet`

在 `src/charMap.ts` 增加一个读入口，接收项目快照的角色数组，逐个转成 `CharacterSheet`；同时让 `toSheet` 对已经是驼峰的输入也能读（先看 `look_cn`，缺失时回退 `lookCn`）。

- 为什么不让服务端同时接受两种形状：服务端契约是唯一事实来源，迁就客户端会把同类 bug 藏起来，也会让第三方调用方以为两种形状都合法。
- 为什么不逐处 `map(toSheet)`：一共五处消费点，逐处补会把「哪些地方必须转换」变成口头约定，下一次新工具很容易再犯。一个入口 + 一次 grep 清单可以持续校验。

### 决策 2：内存快照只保存接口形状

`applyProjectDraft` 写成功后，快照里放回的是转成接口形状的角色数组。

- 备选方案是让快照保存界面形状、写入时再转回。否决原因：快照生产者（`getProject`、`draftCtx`）本来就给接口形状，改语义要动所有生产者；而且 `read_characters` 等工具会把快照内容直接回给模型，保持接口形状才能让模型看到与服务端一致的字段。
- 附带收益：快照里不含 dataURL 图片（接口形状只可能有站内路径），全量重写时不会把浏览器里的临时 dataURL 误写进项目。

### 决策 3：合并阶段对缺失字段防御

判断「已有角色是否已有锚点」时用「取值后转字符串再 `trim`」的方式，缺字段等价于「没有锚点」，继续走补空字段分支。

- 备选方案是严格断言并报错。否决原因：存量库里已经存在锚点为空、字段不全的角色，严格断言会让这些项目永远无法再提交，与「补空字段」的既有语义冲突。

### 决策 4：提交前做本地契约自检，而不是提交后读回

写入前校验：每一条待写入角色都有非空 `name`，且 `look_cn`/`look_en` 与合并结果完全一致；不满足则本次提交失败并说明锚点未保存。

- 备选方案是 `PUT` 之后再 `GET /api/project` 读回比对。否决原因：多一次全项目拉取；而且事务已经提交，读回发现不一致也无法回滚，只能报错，用户还得自己再修。
- 本地自检的价值在于拦住「写出去的东西根本不是蛇形」这一类退化，正是本次事故的直接成因。

### 决策 5：形状边界同样用于三个既有消费点

- 提示词锚点展开：把角色数组按读入口转换后再传给锚点展开。
- 角色三视图 / 表情总图：角色名册与「按名找角色」走读入口，参考图与锚点才能取到真值。
- 台词配音：取角色音色同样走读入口。

这三处与 `submit_characters` 是同一个根因，分开修会让「锚点修好了但仍生成不出图」继续存在。

## Risks / Trade-offs

- [全量重写角色表会丢客户端内存里的临时 dataURL 图片] → 快照固定为接口形状，图片落库仍走 UI 既有的保存通道（`saveCharactersNow`），临时 dataURL 本来就不进项目文件。
- [`toProject` 只保留站内相对路径，远程 URL 图片会被丢弃] → 既有行为，非本次引入；在任务说明里点名，不在本次扩大范围。
- [角色消费点若还有遗漏，仍会读到 `undefined`] → 用一次全仓 grep 清单收敛，并把「提交后读回锚点一致」写成冒烟断言，让遗漏暴露在测试里而不是用户会话里。
- [本地自检依赖服务端字段名稳定] → 服务端字段改名时自检会立即失败，属于期望行为，比静默丢数据更好。

## Migration Plan

- 无数据库迁移，无接口变更，客户端改动随构建发布。
- 存量影响：项目 `a` 的 `幼年白猫`/`成年白猫`/`新角色4` 锚点为空且无历史提交记录可恢复，需用户重新提交一次角色锚点；修复后重新提交不会再丢。
- 回滚：直接回退本次提交即可，不需要数据回滚。
