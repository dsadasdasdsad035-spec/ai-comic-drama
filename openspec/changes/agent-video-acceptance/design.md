# Design

## Context

当前 `finish` 结束的是“代码 + 沙箱 + 关键帧初筛”阶段，MP4 仍由工作台手动渲染；聊天最终文字由文本模型根据工具结果自由生成，视频和聊天没有共享同一个验收产物。另一个现有问题是工作台的「最近视频」和画布右键出片可能使用旧的已保存代码，而聊天展示的是新草稿。参见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- `finish` 后自动进入独立视频验收阶段，最终结论只基于刚渲染的 MP4 帧。
- 视频验收通过后才把代码、参考上下文、MP4 和元数据原子写入当前镜头。
- 聊天明确区分代码阶段、视频阶段和最终完成；失败、取消、无视觉模型都有可恢复状态。
- 旧视频和旧验收不会与当前代码混用。

**Non-Goals:**

- 不新增 agent 渲染/保存工具，不改变 LangGraph 工具循环。
- 不做视频验收失败后的自动修复循环；只提供“继续修复”入口。
- 不校验音频、字幕、剪辑节奏或跨镜头连续性。
- 不改变现有 MP4 渲染、ffmpeg 转码和视频参考协议。
- 不清理未采用的孤儿 MP4 文件；本次只保证不把它们写入镜头数据。

## Decisions

### 1. finish 后的应用编排，而不是 agent 工具

`runSceneAgent` 结束后，`SceneAgentChat` 检查 `result.finished`，再调用新的视频验收编排。渲染、保存、抽帧和视觉验收都在 agent 图之外执行，工具白名单保持不变。

考虑过两种替代方案：

- 增加 `render_video` / `review_video` 工具：模型会参与一次昂贵且不应由它决策的渲染，容易进入循环，还要放宽现有工具约束。
- 在 `finish` 工具内部同步渲染：会占用工具超时预算，且 `finish` 结果要等视频完成，语义更混乱。

选择应用编排的原因是它可以独立超时、独立取消、独立展示进度，也能保证“视频验收不是 agent 自己宣布通过”。

### 2. 最终证据只使用 MP4 帧

视频阶段先用最终代码和本次参考上下文渲染 clean MP4，保存为可访问 URL，再用现有 `/api/frames` 从该 MP4 抽帧，最后把这些帧交给视觉模型。

不使用沙箱帧作为最终证据，因为沙箱帧只能证明代码能渲染，不能证明保存下来的 MP4 内容和聊天结论一致。MP4 URL 同时用于播放器、抽帧和验收卡，三者共享同一个 `videoUrl`。

### 3. 通过才保存；失败保留旧结果

保存策略：

- MP4 帧验收全部通过：原子保存最终代码、参考上下文、MP4、`sceneCodeMeta` 和 `scheduleMeta`。
- 视频验收未通过：不写镜头数据，旧视频和旧元数据不变；聊天保留 MP4 预览和失败项。
- 无视觉模型或抽帧失败：MP4 可预览，状态为“需人工验收”，提供人工采用/保存入口。
- 渲染失败、保存失败、取消或超时：不覆盖旧数据，显示原因和重试入口。

考虑过“无论结果都保存视频”和“始终只在聊天预览、不保存”两种方案。前者会用失败视频覆盖镜头，后者不能满足最终产物落库；选择通过后保存，兼顾安全和可用性。

### 4. 固定本次运行的上下文快照

`prepareAgent` 除了素材和 media brief，还要返回当次运行的 `Shot3DContext` 快照。视频验收成功后，`onVideoAccepted` 使用这个快照持久化，不重新读取可能已被用户修改的工作台状态。

否则用户在 agent 运行期间修改参考内容，聊天帧、视频帧和最终保存的上下文可能来自三个版本。视频阶段使用的代码、素材、上下文、时长和画幅必须来自同一次运行。

### 5. 视频和视频验收使用新的消息 parts

新增 `video` part 和 `video-review` part，不复用 `review_frames` 的工具卡。视频不是 agent 工具，强行塞进工具卡会模糊来源。

`video` part 包含 `videoUrl`、`codeHash`、`duration`、`aspect`、`frames` 和阶段状态；`video-review` 包含逐项结果、帧时间点、视觉模型标识和最终是否保存。帧来源明确标记为 `mp4`，沙箱关键帧继续标记为 `sandbox`。

`finish` 卡片标题改为“代码阶段完成”，不再显示“场景完成”；最终完成状态由视频验收卡决定。

### 6. 最终文字由结构化结果生成

最终聊天文字由确定性模板生成，至少包含：

- `codeHash`
- 沙箱和关键帧初筛结果
- MP4 时长、画幅和 URL
- MP4 帧验收的通过/失败项
- 是否已保存

文本模型的 `finish` summary 只作为“代码阶段说明”，不参与最终完成判定，也不允许它扩写未在 MP4 帧中验证的画面细节。考虑过让第二个模型生成摘要，但这样又会引入不受约束的叙述，选择确定性模板。

### 7. 独立进度、超时和取消

视频阶段状态机：

```text
code_finished
  -> rendering
  -> saving
  -> extracting
  -> reviewing
  -> passed / rejected / needs_human / failed / cancelled / timeout
```

建议独立的超时预算：渲染按镜头时长计算并设上限，抽帧和视觉验收各有单独超时，整个视频阶段有总上限。视频阶段使用与 agent 运行相同的取消按钮和 AbortSignal；切换聊天/代码页签不取消，关闭工作台或用户点击取消会中止。超时或取消不保存新视频。

### 8. 帧采样覆盖全时长

5 帧用于短镜头，9 帧用于长镜头；时间点从 0 到有效时长均匀分布，包含首尾。旧实现固定 `0..4` 秒，长镜头会漏掉后半段，本次不再沿用。

MP4 帧沿用现有联系表（带时间标签）和视觉清单，但提示词明确“帧来自最终 MP4”，并要求每项给出具体依据；无法从画面确认时判为失败或不可见，不能顺着清单确认。

### 9. 旧视频和旧验收显式失效

代码卡、视频卡和验收卡都携带 `codeHash`。当前草稿哈希变化后，旧视频和旧验收显示为过期；工作台「最近视频」不再只是一个无状态链接，而是根据 `isSceneCodeFresh` 显示“生效/已过期/需重渲”。

画布右键 `生成调度视频（3D）` 在工作台存在未保存草稿时不应静默使用已保存旧代码；应用层需要知道当前编辑器的节点和 dirty 状态，提示先保存或在编辑器渲染。这样可以从入口上消除“聊天新代码、画布旧视频”的错配。

### 10. 可测试的依赖注入

视频验收编排提供可注入依赖：render、save、extract、review、persist。图测试和 mock UI 测试使用假依赖验证状态机和保存门禁；真实浏览器测试使用实际 MP4 渲染、`/api/frames` 和 `/api/vision` 验证一条完整链路。错误分类至少包括 `render_failed`、`save_failed`、`extract_failed`、`vision_unavailable`、`review_failed`、`cancelled`、`timeout`。

## Risks / Trade-offs

- **渲染耗时导致聊天变慢** → 独立进度、独立超时、可取消；不把视频阶段算进 agent 推理步骤，但仍显示总耗时。
- **失败验收产生未采用的 MP4 文件** → 只保证不写入镜头数据；孤儿清理不在本次范围，后续可按临时目录或引用计数处理。
- **视觉模型仍可能误判** → 用 MP4 帧证据、逐项原因和确定性最终文字降低影响；无视觉模型时明确转人工，不伪造通过。
- **通过后自动保存会覆盖旧视频** → 只有全部通过才保存；失败、取消、超时、保存失败都保留旧数据，并显示可恢复状态。
- **用户运行中修改参考内容** → 使用本次运行的上下文快照，并以快照原子保存；画布入口增加未保存草稿保护。
- **长视频抽帧/联系表过大** → 时长仍限制在现有 2–12 秒；9 帧上限和现有联系表尺寸足以覆盖。
- **保存成功但视频文件丢失** → 保存后校验 URL/元数据一致性；刷新后由现有 freshness 检查标记问题，不静默复用。

## Migration Plan

- 无数据库 schema 迁移；新增的消息 part 和状态字段都是可选的，旧项目、旧视频和旧聊天记录继续可打开。
- 新行为只对本次之后完成的 agent 运行生效；刷新前已存在的视频按现有 freshness 规则处理。
- 上线后默认对通过代码阶段的运行启用视频验收；回滚时可关闭该阶段，恢复“finish 后手动渲染”，已生成的未采用 MP4 不会影响项目数据。
- 先落编排和 mock 测试，再接真实 MP4 渲染和浏览器验收；最后补画布未保存草稿保护，避免新旧两条出片链路同时存在。

## Open Questions

无。自动视频验收默认开启、失败不自动重跑、未采用 MP4 不清理都已在 Non-Goals 或 Decisions 中确定；不影响后续实现。
