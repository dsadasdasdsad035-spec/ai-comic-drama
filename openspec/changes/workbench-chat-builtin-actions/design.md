# Design

## Context

- 五个内容工作台通过 `WorkbenchChatAdapter` 接入 `SkillChat`：聊天模型拿到 `read_*` 工具和一个 `submit_*` 草稿工具，`runStageAgent` 是通用 JSON-action 工具循环（默认最多 16 步、总时长 180s）。
- 顶部一键按钮走的是另一条路：`buildBoardSkillPrompt(skillId, inputs, 'inline')` + `callText` + `assertSkillOutput` + 宿主合并。角色拆解目前在 `App.tsx`，其余在各工作台组件里。
- 两条路的输入处理不同：`buildSkillPrompt` 在 `'chat'` 模式下把超过 2000 字的输入替换成引用行，依赖 `read_*` 工具按范围读取；`'inline'` 模式完整内联。分镜的 `brief` 是本地文本框，可能尚未保存，读工具读不到；角色/素材的“全剧”范围也只存在于按钮。
- `callText` 支持 `AbortSignal`；现有按钮没有把取消信号接进去。
- 基座变更 `skill-driven-workbench-chats` 当前 39/40，主规格 `workbench-chat` 尚未归档；本变更会改同一批聊天文件。

## Goals / Non-Goals

**Goals:**

- 每个工作台聊天都有与顶部按钮一一对应的内置动作，且结果、数量、保存语义完全一致。
- 按钮与聊天动作共用一条宿主执行路径，避免提示词/合并逻辑漂移。
- 内置动作在模型循环外运行，复用任务台账、进度、取消，不增加模型工具和嵌套模型调用。
- 动作结果以结构化回执进入线程，重新打开仍在，下一轮模型只看到摘要。
- 保持现有聊天读写边界：模型仍只读上游、只提交自己的工作台草稿。

**Non-Goals:**

- 不做模型可调用的 `run_builtin` 工具（后续 A2 需要确认门禁、更长超时和成本提示）。
- 不做跨工作台的统一聊天或跨工作台写入。
- 不改变 3D 工作台聊天、工具和验收。
- 不改变技能文件、输出契约、合并算法或保存语义。
- 不新增项目数据字段，不需要数据迁移。

## Decisions

### 1. 内置动作作为 adapter 的一部分，而不是硬编码在聊天壳里

`WorkbenchChatAdapter` 增加：

```
BuiltinAction {
  key, label, hint?
  scope?: 'episode' | 'script'
  disabled?: () => { disabled: boolean; reason?: string }
  run: (signal?: AbortSignal) => Promise<BuiltinResult>
}

BuiltinResult {
  ok, action, scope?, summary, counts?, modelLabel?, elapsedMs?, saveMode?, error?
}
```

工作台把自己的动作列表交给 adapter；`SkillChat` 只负责渲染、禁用态、运行态和回执。动作的 `run` 由宿主提供，聊天壳不知道技能 id、输入模板或合并规则。

替代方案：在 `WORKBENCH_PROFILES` 里放固定动作表。否决：运行函数、范围、禁用原因都是工作台私有逻辑，塞进全局 profile 会把宿主逻辑带到聊天壳。

### 2. 顶部按钮和聊天动作调用同一个宿主函数

把五个一键函数收敛为“返回结果 + 接受信号”的宿主回调；按钮和 `BuiltinAction.run` 都调用它。角色拆解从 `App.tsx` 收进共享回调（或由 App 注入），避免按钮与聊天各有一套 `mergeCharacters` 调用。

替代方案：聊天动作复制按钮里的 `buildBoardSkillPrompt` + `callText` + merge。否决：两份逻辑必然漂移，且测试无法保证“结果一致”。

### 3. 内置动作在模型循环之外运行

动作是用户点击的 UI 行为，不是模型工具：

```
点击内置动作
   -> adapter.builtins[i].run(signal)
   -> 宿主：inline 技能 + callText(signal) + assertSkillOutput + merge/save
   -> 任务台账 / 进度 / 错误
   -> builtin 回执
```

不新增 `run_builtin` 工具。这样不会在 agent 循环里再套一次模型调用，也不受 `runStageAgent` 的 180s 总时长和 16 步上限影响。

替代方案：让模型调用内置工具。延后到 A2：需要“建议运行 → 用户确认 → 执行”的门禁、独立超时与成本提示，不适合和 v1 一起做。

### 4. 输入使用完整 inline 与本地草稿

`BuiltinAction.run` 直接调用宿主的一键函数；宿主函数继续用 `buildBoardSkillPrompt(..., 'inline')` 和本地状态。它不读取聊天 `'chat'` 模式的引用行，也不依赖 `read_*` 工具。

这解决了两个真实差异：

- 分镜 `brief` 超过 2000 字时聊天只拿到引用行，而本地 `brief` 没有对应读工具；
- 角色/素材的“全剧”范围需要项目级上下文，聊天 adapter 的 `inputs()` 固定当前集。

动作回执里展示实际范围与输入规模（例如“全剧 8 集 / 3,200 字”），让用户知道这次跑了什么。

### 5. 范围显式化，保存语义沿用工作台

- 剧本：生成分集（全剧，替换当前分集草稿）。
- 角色：从本集拆角色 / 从全剧拆角色。
- 素材：从本集拆 / 从全剧拆。
- 镜头表：拆镜（当前集）。
- 提示词：生成提示词（当前集，沿用分批并行）。

保存语义继续由 `WorkbenchSaveMode` 决定：剧本/镜头/提示词显式保存；角色约 1s 自动；素材立即。回执必须写出“未保存 / 约 1 秒后落库 / 已落库”。

### 6. 结果以 `builtin` 回执进入线程

在聊天消息模型里增加一个 `builtin` part（动作、范围、摘要、数量、模型、耗时、保存语义）。`StageToolUis` 渲染一张动作卡；线程持久化只存摘要，不存整份产物。下一轮 `threadTranscript` 只带摘要，模型可以在摘要基础上继续用 `submit_*` 改稿。

替代方案：把结果拼成一条 assistant 文本。否决：无法区分“动作回执”和模型发言，重新打开后也无法稳定渲染。

### 7. 单工作台互斥与禁用原因

每个工作台维护一个“忙碌”状态：`genning` / `extracting` / `chatRunning` 任一为真。动作运行中禁用聊天发送、顶部按钮和其他动作；聊天模型运行中禁用动作。禁用必须给原因（无项目、无文本模型、输入为空、已有动作在跑）。

替代方案：允许动作与聊天并发。否决：两条路径都会改同一份草稿，合并顺序不可控，还会重复花费。

### 8. 取消使用 `AbortSignal`

`callText` 已支持 `AbortSignal`。动作自己持有 `AbortController`：

- 单次动作：取消 → 中止请求 → 不调用 merge/save。
- 提示词分批：所有批次共享同一个信号；任一批失败/取消 → 整次动作不合并，丢弃已完成批次的结果。

顶部按钮是否也获得取消按钮不在 v1 的强制范围；聊天动作先具备。

### 9. 入口：空态主按钮 + 头部紧凑入口

- 空态：在 `WorkbenchEmpty` 上方渲染动作按钮，替换现有“用上方的…”文案。
- 首轮之后：头部或工具栏保留一个“内置动作”入口（菜单或一排小按钮），避免用户往上翻。
- 顶部按钮保留，两条入口都能用。

替代方案：只在头部放入口。否决：新用户第一眼看不到“从零生成”，空态更需要它。

### 10. 依赖与落地顺序

基座变更 `skill-driven-workbench-chats` 的 4.7 仍是文档/真实全流程验收；主规格未归档。本变更与它改同一批聊天文件，因此：

- 现在只捕获规划产物；
- 实施排在基座变更完成/归档之后，或至少避免两个 apply 同时改这些文件；
- 本变更以新能力 `workbench-chat-actions` 独立存在，不依赖尚未归档的 `workbench-chat` 主规格做 delta。

## Risks / Trade-offs

- [任务台账 + 聊天卡双份进度] → 以工作台的任务台账/状态为唯一真相；聊天卡只镜像，不另开计时器。
- [按钮与聊天动作结果漂移] → 单一宿主函数 + 同输入一致性测试；两条入口都走 `assertSkillOutput` 和同一 merge。
- [取消后留下半份草稿] → 只有全部批次成功并校验后才 merge；取消/失败一律丢弃。
- [提示词分批耗时较长] → 复用现有并发与进度；动作在 agent 循环外，不受 180s 影响；提供取消。
- [回执把整份产物塞进线程/下一轮上下文] → 只持久化摘要与数量；完整产物留在工作台草稿。
- [角色拆解仍分散在 App] → 收敛为共享宿主回调；按钮与聊天都调用它，测试两条路径一致。
- [用户以为模型会自己调用内置动作] → 文案明确“动作由你点击运行”；A2 若做，需要确认门禁。
- [与基座变更冲突] → 先完成/归档基座；本变更规划可独立，apply 顺序明确。
- [窄屏聊天空间不足] → 空态用整行按钮，首轮后用头部菜单；不占用输入框高度。

## Migration Plan

- 无数据迁移；不新增项目字段。
- 先把 `builtins` 作为 adapter 的可选字段接入，未提供时聊天行为不变；可隐藏/关闭入口做灰度。
- 回滚：隐藏动作入口即可，顶部按钮不受影响；已产生的动作回执是线程消息，不清洗也不影响加载。
- 部署：纯客户端改动，无服务端 API 变化。

## Open Questions

- 顶部按钮是否也补一个取消按钮（聊天动作已有取消）。可以在动作稳定后单独做，不影响规格与任务拆分。
- 动作回执中的“查看本次完整输入”是否复用现有检查器，还是只显示规模/范围。v1 可以先显示规模与范围。
- 首轮后的入口用头部下拉还是一排小按钮，属于 UI 细节，按窄屏空间实现时定。
