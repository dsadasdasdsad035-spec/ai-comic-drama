# Design

## Context

参见 `proposal.md` — Why。实测约束：

- `mergeShots(existing, incoming)`（`server/data.mjs`）对未出现在 `incoming` 里的镜头只做 `{...s, orphan: true}`，**从不删除**。实测：提交 `[S01, S03]` 而库里有 `[S01,S02,S03]`，结果是 `S01, S03, S02(orphan)`。
- `orphan` 不是软删除：它只在 UI 里多一个「孤儿」标签（`src/ShotTable.tsx`、`src/PromptTable.tsx` 都渲染），`visible` 过滤只看 `episode`，所以孤儿镜头在镜头表、提示词表里仍然存在、仍会被算进总数与时长。
- 画布的 `removeShot(id)`（`src/App.tsx`）只从 `nodes` 与 `edges` 里移除，不动 `project.shots`。
- `saveProject`（PUT，整表替换）已实现但**没有任何调用方**。
- `buildShotNodes(prev, shots)` 按 `shotId` 复用节点位置，只为 `shots` 里的镜头建节点——所以真删掉后重建画布，节点会消失。
- 镜头 `id` 由 `E{补零集号}-{镜号}` 生成（`src/agent/shotDraft.ts`）。实测：两条 `no` 相同的镜头会拿到相同 `id`；服务端 `mergeShots` 对 `incoming` 里的重复 `id` 会都保留（现有库里没有时），但一旦与既有数据合并就会互相覆盖。
- `episodes` 与 `designs` 在 `POST /api/project` 是整表替换（`vite.config.ts`），所以场次的删除与设定卡的删除**已经天然可行**，缺的只是 UI 入口。
- 只有 `shots` 走字段级合并，所以只有镜头需要新的删除能力。

## Goals / Non-Goals

**Goals:**

- 三种「人删一行」都有真正落到数据的路径，不依赖改 JSON。
- 把「缺席 = 保护」与「显式 = 删除」分清楚，不破坏 `orphan` 原有的防误删作用。
- 删除后的引用一致性由代码保证，不靠用户记住去清转场。

**Non-Goals:**

- 撤销/回收站。
- 自动重排镜号或场次号。
- 批量选择删除、拖拽排序、跨集移动。
- 删除整集（已有，且它本身不删镜头）。

## Decisions

### 决策 1：删除走 `deleteShotIds`，不改成 `presentIds` 反向推断

`POST /api/project` 增加可选字段 `deleteShotIds: string[]`。服务端在应用 `shots` 合并之后、写盘之前，把命中 id 的镜头从数组里移除。

替代方案 A：把 `mergeShots` 改成「以提交列表为准，缺席即删」。否决理由——`orphan` 存在的理由就是防「模型只返回部分镜头时静默删掉其余」，改成缺席即删会直接毁掉这层保护（`workbench-text-intake` 的 merge 语义也依赖它）。

替代方案 B：前端改用 `PUT` 整表替换。否决理由——PUT 没有任何调用方，且整表替换会把并发编辑与其他集的数据一起覆盖，风险大于收益。

**顺序很重要**：先合并 `shots`、再删 `deleteShotIds`。这样同一请求里「更新一批 + 删一条」也能表达，且删除对合并后不存在于提交列表的 orphan 也生效（删除动作不要求把该镜也放进 `shots`）。

### 决策 2：删除时的引用清理在前端完成，服务端只做 id 移除

服务端删完镜头后，不知道自己该不该改别的镜头的 `transition_out`——那是业务语义。所以前端在提交前就把草稿改好：

```
删除 shot X：
1. 从 shots 移除 X
2. 遍历剩余镜头，清掉 transition_out.to === X.id 的
3. deleteShotIds 里加入 X.id
4. 画布：移除 shotId === X.id 的节点与相关边
```

服务端额外做一层兜底：写盘后扫描 `transition_out.to` 指向已不存在镜头的条目并清除，因为导入、手动编辑 JSON 等路径也可能留下悬空引用。

替代方案：服务端全权负责清理。否决理由——服务端要理解 `transitionOut.to` 表示的是「目标 shotId 或画布节点 id」（`src/App.tsx` 里 `tgt.data.shotId || tgt.id`），这个双语义只有前端清楚。

### 决策 3：孤儿镜头提供「清理」入口，但不自动删

删除能力上线后，历史 `orphan` 镜头会变成可见的遗留项。不自动删（那正是保护逻辑要避免的事），而是在镜头表提供「清理孤儿」按钮：列出所有 `orphan` 镜头，用户勾选后走同一条 `deleteShotIds` 路径。

这样「孤儿」从一个只增不减的状态变成可治理的状态，同时保持「默认不删」。

### 决策 4：镜号唯一性校验放在保存前，且区分集

校验键是 `(episode, no)`。前端在 `save()` 前算一次，重复时列出冲突行并阻止保存；服务端在 `mergeShots` 之后也校验一次，重复则拒绝写入并返回明确错误。

**为什么必须服务端也校验**：镜号不仅决定显示，还决定导入与生成的 `id` 生成（`E{集}-{镜号}`）。重复镜号会让后续任何一次「拆镜」或「导入」产生同 id 的两条记录，然后相互覆盖。这是数据损坏级别的隐患，不能只靠前端。

替代方案：把 `id` 改成随机 uid，与镜号解耦。否决理由——`id` 稳定是幂等推送、画布节点复用、导入合并的基础；改成随机 id 会让「重新拆镜」每次都产生新镜头。`E{集}-{镜号}` 的方案是刻意的，代价就是镜号必须唯一。

### 决策 5：新镜号取「集内最大号 + 1」，不填补空洞

用户删掉 `S02` 后再新增，新镜号是 `S07` 而不是复用 `S02`。理由是复用空洞会让人误以为这是原来那一镜，而 `id`（`E01-S02`）若是复用的，还可能命中仍残留在别处的引用。

**代价**：镜号会出现不连续。接受，因为镜号是标识不是序号；如果用户在乎连续性，可以手动改。

### 决策 6：场次与设定卡的增删不加服务端能力

`episodes` 与 `designs` 走整表替换，删除只要从数组里去掉即可。但要补两处保护：

- 删场时检查该场下是否有镜头（`shot.scene_no === 该场号`），在确认框里报数量。不阻止删除——`scene_no` 变成悬空值后，镜头仍可正常生成与出片，只是失去场次归属；`scheduleContext` 一类读取要能容忍查不到的场次。
- 删设定卡时，画布上已发布的素材卡不跟着删（现有行为就是「只删设定，不删画布卡」），确认框要说明。

### 决策 7：画布的「删除卡片」增加「同时删除镜头数据」勾选

现在画布上的删除只删节点，用户会以为镜头也没了（切到镜头表又出现）。改成确认框里提供勾选，默认不勾（保守），勾选时走同一条 `deleteShotIds` 路径。

替代方案：让画布删除默认同时删数据。否决理由——画布上还有示例卡与手工卡，把「删节点」和「删业务数据」绑死会让一次误点丢镜头。

## Risks / Trade-offs

- **删除后无法撤销** → 确认框写明镜号、产物情况，并提示可从 `project.json.bak` 找回；不做回收站。
- **孤儿清理按钮可能被误用删掉大量镜头** → 必须逐条勾选，不提供「全选删除」；列表显示每条的镜号与产物情况。
- **镜号不连续让人困惑** → 不在本期解决；若用户强烈需要，后续可加「重排镜号」显式动作（需同时改 id 并迁移引用，属独立变更）。
- **`deleteShotIds` 与 `shots` 同时提交时的顺序歧义** → 固定为「先合并后删除」并写进规格与验收；同一 id 同时出现在两处时以删除为准。
- **场次号重复**（与镜号同类问题）→ 本期只校验镜号；场次号重复的影响限于场次归属与 3D 场景复用，不会造成 id 碰撞，留待观察。
- **导入与手工加行同时存在时的 orphan 增长** → `merge` 语义使孤儿不再因导入产生；历史孤儿用清理入口治理。

## Migration Plan

无数据迁移。历史 `orphan` 镜头保持原状，通过清理入口由用户决定是否删除。

部署顺序无要求：`deleteShotIds` 是可选字段，旧客户端不传即保持现有行为。

回滚：撤掉 UI 入口与 `deleteShotIds` 处理即可；已删除的数据无法通过回滚恢复（依赖 `project.json.bak`）。
