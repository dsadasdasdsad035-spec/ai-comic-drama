# Design

## Context

见 `proposal.md - Why`。当前实现里封面链路的分层是这样的：

- 前端 `CoverPicker` 产出封面地址（抽帧为 dataURL，上传为 `/api/save-image` 返回的 `/generated/...`）；
- 服务端 `normalizeDeliverableConfig` 负责持久化与读取时的白名单收窄；
- `runPreflight` 用 `resolvePublishFile` 判定封面文件是否可用；
- `publish-queue` 组装适配器上下文并驱动 `uploadVideo → fillMetadata → saveDraft`；
- 适配器按声明式步骤表操作页面。

三处断点分别落在第 2、1、4 层，且互不报错：抽帧产物在持久化时被截断，比例白名单把 3:4 / 4:3 丢掉，适配器上下文里没有封面。约束是：本仓库的平台选择器全部处于 `verified: false` 状态，代码原则是「选择器未在真实登录态验证前不盲点」。

## Goals / Non-Goals

**Goals:**

- 四档封面比例在保存与读取链路上对称，不再有静默丢弃。
- 抽帧与上传产出一致：都是服务端可解析、刷新后仍存在的文件引用，且图片实际符合所选比例。
- 自动流程要么真的把封面上传到平台，要么如实说明没上传；阶段文案不再与实际动作不符。
- 用验证用例锁住这三类回归，避免再次出现「测试全绿但封面不对」。

**Non-Goals:**

- 不在本变更里把任何适配器标记为 `verified`：真实封面上传选择器需要登录态人工核对，属于独立验收步骤。
- 不为封面做重渲染或视频封面替换；不改变平台能力表中的封面比例声明。
- 不回填历史配置：被丢弃的 3:4 / 4:3 无法还原，用户需要重新准备。

## Decisions

### 决策 1：封面比例以平台能力表为唯一来源，规范化接受其并集

`server/publish-platforms.mjs` 已经声明了每个平台需要的比例，并导出 `COVER_ASPECT_ORDER`。把它扩为导出完整的 `COVER_ASPECTS`（四档），`server/deliverables.mjs` 直接引用该集合做白名单，前端 `src/publish/types.ts` 的类型枚举保持不变（它只是类型与展示顺序）。

替代方案是两边各维护一份常量并加测试比对——被否决：这正是当前 bug 的成因，两份常量迟早再漂移。改为「服务端能力表即白名单」，并在契约验证里断言「每个平台声明的每个比例都能被规范化保留」，把漂移变成测试失败而不是静默丢数据。

规范化时只接受以 `/` 开头的站内地址；不以 `/` 开头的值（包括 `data:` 内联数据、历史被截断的残片）一律丢弃，让预检按「该比例缺失」报告，而不是把坏地址带进发布包。

### 决策 2：抽帧在浏览器端裁切后立即落盘

抽帧仍在前端完成（不引入服务端 ffmpeg 依赖，也不上传整段视频）。变化有两点：

1. canvas 按目标比例做居中裁切（cover 语义）后再编码，保证输出图片的宽高比与所选比例一致；现有实现总是沿用成片原始比例。
2. 编码结果先 `POST /api/save-image` 落盘，拿到 `/generated/...` 地址后才写入配置。`/api/save-image` 已接受 `prefix` 字段（当前 `CoverPicker` 误传 `name`，导致文件名退化为 `sheet-*`），修正为 `cover-<比例>`。

助手 `set_cover(source=frame)` 复用同一套逻辑：抽帧 → 裁切 → 落盘 → 返回地址。这样助手与手动路径产出同形结果，满足 `publish-assistant` 的「与手动准备一致」。

替代方案是让服务端提供抽帧接口直接返回文件地址——被否决：会把视频解码搬到服务端，且与现有「抽帧纯前端」的取舍相反；落盘复用已有接口，改动面最小。

### 决策 3：适配器上下文增加封面，能力用三态声明

`publish-queue` 在组装上下文时按 `platform.coverAspects` 顺序取第一个已准备的比例，解析为绝对路径后放入 `ctx.coverPath`，同时放入 `ctx.covers`（比例 → 绝对路径）供需要多比例的适配器使用。缺失时为 `''`，由适配器与任务汇报处理。

适配器注册项新增 `coverSupport`，取值：

- `supported`：适配器实现了封面上传步骤，且选择器已在真实登录态验证过；
- `unverified`：实现了步骤或接口，但选择器未在真实登录态验证（本变更结束时的默认值）；
- `unsupported`：该平台没有自定义封面入口。

`saveDraft` 之前的封面动作只在 `supported` 时执行；`unverified` 与 `unsupported` 都不点击未知选择器。任务在结束时把真实结论写进事件与 payload：`coverAttached: true/false` 与原因。这样「阶段说明写封面、实际没传」这类谎报在数据层就不可能出现。

替代方案是直接给抖音/B 站加上「点设置封面 → 上传」的步骤并标记 `supported`——被否决：违反仓库既定的「未验证不盲点」原则，且失败会表现为选择器超时，比现状更难归因。真实步骤与验证流程作为单独的任务，验证通过后再改 `coverSupport`。

### 决策 4：预检对「封面无法自动投递」给出警告

当已选平台的适配器 `coverSupport !== 'supported'` 且该平台需要封面时，预检追加一条 `warn`（不是阻断）：说明该平台的封面需要在后台手动确认。用户仍可提交草稿，但不会再以为封面会随任务一起上去。阻断仍然只留给「缺封面文件」这类配置问题。

## Risks / Trade-offs

- [真实平台封面上传仍未打通] → 本变更把链路与能力声明做对，并在预检与任务记录中如实暴露；真实选择器由独立任务在登录态下验证后翻转 `coverSupport`，不静默假装完成。
- [裁切改变构图] → 采用居中裁切，与平台封面「填满框」的展示语义一致；用户仍可用「上传图片」自行提供精确构图。
- [`/generated/` 封面随成片累积] → 文件名带时间戳与比例，不覆盖他人文件；不引入清理机制（与现有 `save-image` 行为一致），作为已知限制记录。
- [历史配置里存在 500 字符的 dataURL 残片] → 规范化后按缺失处理，预检明确提示重新准备；不做静默修复。
- [适配器上下文新增字段可能影响测试替身] → 现有验证脚本的假适配器忽略多余字段，向后兼容。

### 未完成：真实平台封面选择器验证（2026-10-26）

任务 5.1 / 5.2 无法在本机完成，实际阻塞原因：

- 本机 `data/projects/.publish-profiles/` 下 6 个 profile 目录全部为空，发布账号表 0 条记录，没有任何已登录的抖音 / B 站会话；
- 打开创作者后台并核对「设置封面」入口需要人本人在有头浏览器里扫码登录，自动化脚本不能代做，也不应绕过平台验证；
- 因此无法取得选择器证据，也无法在真实登录态跑一次草稿任务确认封面生效。

结论：7 个内置适配器的 `coverSupport` 一律保留 `unverified`，`uploadCover` 未实现。当前行为是「不点未知选择器 + 预检警告 + 任务记录 `coverAttached:false`」，比之前「声称填写封面但实际没填」更诚实，但不等于封面上传已经打通。补齐这一步需要：

1. 人工用发布台的「连接账号」登录抖音与 B 站（各一次扫码）；
2. 在真实后台核对封面入口的 DOM，把步骤写进对应适配器并实现 `uploadCover`；
3. 把该适配器的 `coverSupport` 改为 `supported`，`verified` 另行评估；
4. 跑一次真实草稿，确认平台草稿里的封面是所选图而不是自动截帧。

## Migration Plan

无数据库迁移。部署后：

1. 已有成片配置中若存在 3:4 / 4:3 封面（实际已被丢弃）或 dataURL 残片，预检会提示缺失，用户重新选择即可。
2. 回滚只需回退代码；数据库中不会写入新结构，旧代码仍可读取（四档配置在旧代码下会被再次丢弃，属于可接受的回滚代价）。
