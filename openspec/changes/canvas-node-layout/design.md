# Design

## Context

参见 `proposal.md` - Why。现状的约束：

- 节点位置有三个存储源：镜头节点在 React Flow `nodes` 状态（经 `localStorage` 持久化）、角色卡位置在 `storyboard-char-pos`、素材卡位置混在 `nodes` 里。
- 水合入口 `composeShotCanvasNodes` 只决定**顺序**，`buildShotNodes` 决定**位置**：有旧节点就复用其 `position`，没有才现算。角色卡与素材卡的位置则在 `App.tsx` 的多个 effect / 回调里内联计算。
- 卡片尺寸不完全由数据决定：分镜卡宽度随时长变化（250~380），角色卡与素材卡是 CSS 固定尺寸。新增节点的那一刻还没有 React Flow 的实测尺寸。

## Goals / Non-Goals

**Goals**

- 一个可单测的落位实现，所有创建入口复用它。
- 默认落位不重叠，且分区稳定。
- 已有位置在数据变化时不被改写。

**Non-Goals**

- 不引入通用图布局算法（dagre / elk）或新的布局依赖。这里的布局是规则化的分带栅格，不是任意图。
- 不改 `project.shots` / `project.assets` 的数组顺序，也不改 `read_shots` 的读出顺序。
- 不做布局的撤销/重做。

## Decisions

### 1. 新建纯函数布局模块

新增 `canvasLayout` 模块，导出三件事：区域常量、`placeNewNode(kind, existing, opts)`、`arrangeAll(nodes, opts)`。不依赖 React / React Flow，便于单测与在 effect 外复用。

**为什么不放在 `canvasShots.ts`**：那个文件已经有水合与连线的职责，且只服务分镜；角色与素材的落位需要同一套区域常量，放一起会让它变成四类节点的杂货铺。

### 2. 尺寸用保守常量，不用实测尺寸

新节点落位时拿不到 `measured`，因此模块内按节点类型维护一组保守的估算尺寸（分镜：`cardWidth(seconds)` 宽 × 高度按 16:9 画面加头尾估算；角色卡 120 宽；素材卡 200 宽）。避让判定用「估算矩形 + 间距」。

**代价**：估算略大于真实时会出现偏大的空隙；估算偏小时仍可能轻微重叠。取舍是保守取大。

**替代方案**：等渲染后读 `measured` 再修正位置 —— 会造成可见的跳动，且需要额外的 effect 链，否决。

### 3. 分镜列宽按已占用宽度累加

同一集内，按镜号升序逐张累加 `x_next = x_prev + width_prev + gap`。不再用 `col * (自身宽度 + gap)`。

**为什么不用固定列宽**：固定最大列宽（380）会让 3 秒短镜之间出现 100+px 的空洞，视觉上像断链。累加让同行卡片紧贴且不重叠。

**注意**：累加后同集不同行的总宽度不同，这是可接受的；行内对齐属于打磨，见 Open Questions。

### 4. 落位顺序由镜号数值决定

`buildShotNodes` 目前按 `shots.map((sh, i))` 的下标累加 `col/row` 计数器。改为先按「集号升序 + 镜号数值」得到落位序列，再累加。已有位置的节点跳过计算，但仍占位（参与避让）。

**为什么要改**：写回顺序会漂移（`mergeShots` 把命中镜放到前面），而下标决定槽位，导致新增镜头的落点不可预测。按镜号落位与相邻镜判断（`sortedEpisodeShots`）用同一个依据，行为一致。

**风险**：镜号非数字（历史脏数据）时排序不稳定 → 用与 `compareShots` 相同的兜底（先数值，再本地化字符串比较，最后按 id）。

### 5. 区域常量集中定义，素材带统一在上方

定义三个纵向带：角色带、素材带、分镜带，各自有起始 y 与行间距；素材带在分镜带上方（负 y 方向延伸），角色带在素材带之上贴近。

首次恢复与运行时新增**共用**素材带，消除「同一批卡因来源不同落在两个区域」的问题。

**兼容**：已经在 `y=-560` 附近的存量素材卡保留原位；只有新增与整理会进入新常量。

### 6. 「整理画布」放在画布工具条，不弹确认

动作只改位置，不改任何业务数据，且再点一次可重复执行，因此不打断用户。按钮与「适配视图」「整理」并列。

实现上分两步写回：镜头/素材卡位置写 `nodes` 状态并由既有 `localStorage` 持久化；角色卡位置写 `charPos` 与 `storyboard-char-pos`。两步都在同一个动作内完成，避免一半新一半旧。

### 7. 保留既有的节点身份逻辑

`buildShotNodes` 里「按 shotId 认领旧节点、同集镜号重复时去重、演示卡退场」这些规则不动；本次只替换「算位置」那一段与落位序列。

## Risks / Trade-offs

- [用户已摆好的画布在打开后观感变化] → 已有节点位置一律保留；变化只影响新增节点与显式整理。
- [估算尺寸与真实尺寸不符造成轻微重叠] → 估算取保守上限；验收用例覆盖宽窄混排。
- [按镜号落位让「先建的镜占据更靠前的位置」] → 这正是期望行为；若用户希望按创建顺序，可用手工拖放或整理后的位置覆盖。
- [整理动作把用户的精心布局抹掉] → 只在显式点击时执行，且不弹确认意味着误点成本低；后续若反馈强烈再加确认或撤销。

## Migration Plan

无数据迁移。加载时既有节点保留位置；用户可点「整理画布」把历史漂移的布局归位。回滚只需还原前端代码，不影响任何持久化数据格式。

## Open Questions

- 同集内是否要让每行对齐到统一列宽（视觉更整齐，但短镜之间会留白）？可在整理动作里再决定，不影响默认落位。
