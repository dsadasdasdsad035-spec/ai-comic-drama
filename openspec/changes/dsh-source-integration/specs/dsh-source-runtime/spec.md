# Spec Delta

## Purpose

定义创意视图所依赖的 dsh 宿主运行时如何由本仓库自有源码供给：源码的纳管与版本钉定、构建产物的要求、启动入口的解析顺序与失败语义。

## ADDED Requirements

### Requirement: 宿主运行时来自本仓库钉定的源码

应用 SHALL 从一个由本仓库纳管、并在版本上钉定的 dsh 源码构建产物启动宿主。该源码版本 MUST 与应用声明的宿主版本一致。应用 MUST NOT 依赖未在仓库中记录版本的宿主源码。

#### Scenario: 版本一致

- **WHEN** 检查应用声明的宿主版本与源码树所钉定的版本
- **THEN** 两者为同一版本，不存在一处已升级而另一处未升级

#### Scenario: 源码未纳管

- **WHEN** 源码目录未被初始化或不存在
- **THEN** 应用仍可启动，创意视图给出可读的初始化说明，MUST NOT 在启动阶段崩溃

### Requirement: 宿主入口按固定顺序解析并允许显式覆盖

宿主入口 SHALL 按「显式覆盖 → 源码构建产物 → 已安装包」的顺序解析。显式覆盖 MUST 接受一个指向宿主入口文件的绝对路径，且优先于其余两级。应用 MUST NOT 在没有显式覆盖时优先使用已安装包而忽略源码构建产物。

#### Scenario: 显式覆盖生效

- **WHEN** 操作员通过环境变量指定了宿主入口路径
- **THEN** 应用启动该路径对应的宿主，不读取其它入口

#### Scenario: 源码优先于安装包

- **WHEN** 源码构建产物与已安装包同时存在且未指定显式覆盖
- **THEN** 应用启动源码构建产物

### Requirement: 宿主入口缺失时失败原因可区分

宿主入口不可用时，应用 MUST 以可读中文说明失败原因，且 MUST 区分「源码未初始化」「源码存在但未构建」「未安装且未构建」三种情况，并给出对应的补救动作。应用 MUST NOT 用笼统的“未安装宿主”覆盖全部情况。

#### Scenario: 源码存在但未构建

- **WHEN** 源码目录存在而构建产物缺失
- **THEN** 提示指明源码存在但尚未构建，并给出构建命令

#### Scenario: 源码未初始化

- **WHEN** 源码目录存在但内容为空
- **THEN** 提示指明需要初始化子模块，并给出初始化命令

#### Scenario: 两者都没有

- **WHEN** 源码构建产物与已安装包都不存在
- **THEN** 提示同时给出安装与构建两条补救路径

### Requirement: 宿主构建缺失不阻断应用其它视图

宿主源码未构建、构建失败或入口不可用时，应用 SHALL 继续提供工作台、画布等其它视图。创意视图 MUST 给出可读失败说明与重试入口，MUST NOT 显示空白页或原始堆栈。

#### Scenario: 未构建时的整体可用性

- **WHEN** 宿主源码尚未构建，操作员打开应用
- **THEN** 其它视图正常可用，创意视图显示构建相关的可读说明

#### Scenario: 构建完成后恢复

- **WHEN** 操作员完成宿主构建并点击重试
- **THEN** 创意视图正常打开，无需重启整个应用

### Requirement: 源码构建产物包含运行时会用到的原生模块

从源码构建的宿主 SHALL 自带本平台的原生模块（`native/system` 的 flock／landlock）产物。只编译 TypeScript 视为构建未完成：应用 MUST 在构建结束时报出缺失，而不是让宿主在开启会话时以模块加载失败告终。

#### Scenario: 只编译了 TypeScript

- **WHEN** 源码树存在 `apps/cli/lib/bin.js`，但本平台的 `native/system/packages/<平台>/bin/system.node` 缺失
- **THEN** `build:dsh` 的产物校验失败并指出缺失路径，提示重新执行构建

#### Scenario: 原生模块齐备

- **WHEN** 本平台的 `prebuilds.json` 存在且对应产物已生成
- **THEN** 构建通过，创意视图内的一轮会话不再因原生模块缺失而失败

### Requirement: 创意视图经反代后可建立会话通道

创意视图把宿主挂在 `/studio/` 前缀下，宿主 0.2.2-rc.5 的 Origin 围栏要求 `Origin` 与 `Host` 是同一个 authority。反代 MUST 在转发时把浏览器带来的 `Origin` 换成上游 authority（不透明来源 `null` 除外），否则 WebSocket 升级被宿主拒绝，界面停在「重新连接中」。

#### Scenario: 浏览器带 Origin 的升级请求

- **WHEN** 浏览器从 `/studio/` 页面发起 `/studio/api/remote.mux` 的 WebSocket 升级
- **THEN** 宿主收到的 `Origin` 等于它自己的 authority，升级成功，会话列表与会话通道可用

#### Scenario: 不透明来源

- **WHEN** 请求携带的 `Origin` 是 `null`
- **THEN** 反代原样透传，交给宿主拒绝

### Requirement: 宿主插件集合与预期清单一致

宿主启动完成后，应用 SHALL 校验宿主实际启动的插件层与预期清单一致。存在预期插件未启动时，应用 MUST 报告缺失项，MUST NOT 以“少几个插件”的静默状态继续提供创意视图。

#### Scenario: 插件缺失被报告

- **WHEN** 宿主启动后实际启动的插件层缺少预期项
- **THEN** 应用报告缺失的插件标识，并提示可能原因

#### Scenario: 插件齐备

- **WHEN** 宿主启动后实际启动的插件层与预期清单一致
- **THEN** 创意视图正常提供，不产生额外警告
