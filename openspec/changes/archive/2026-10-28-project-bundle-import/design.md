# Design

## Context

参见 `proposal.md` — Why，样本仓库 `github.com/dsadasdasdsad035-spec/cat`。实测约束：

- 样本包 31 个条目、7.4MB 压缩、7.8MB 解压、压缩比 1.01（几乎全是已压缩的 JPEG/PNG）。这决定了**压缩炸弹防护不能只看压缩比**——真实素材包的压缩比本来就近 1，靠 ratio 判定会误杀。
- Node 22 自带 `zlib.inflateRawSync`，实测可解 `method: 8` 的条目；`method: 0`（stored）直接取原始字节。样本里两种方法都有。
- 实测样本的 ZIP 条目**没有设置 UTF-8 标志位**（`flags & 0x800 === 0`），但文件名是裸 UTF-8 字节。macOS `zip` 的典型行为。Node 的 `TextDecoder` 支持 `utf-8` / `gbk` / `gb18030` / `big5`，实测 GBK 解码正常。
- Docker 镜像**没有安装 `unzip`**，且不打算为解包新增系统包。
- 解包后的文本导入已经设计好（`workbench-text-intake`）：格式识别、表头别名、值归一化、`merge` 合并、预览。
- 图片上传已经设计好（`asset-image-upload`）：`mediaUpload` 校验 + `/api/save-image` 落盘。
- 项目媒体目录 `projects/<项目>/assets/` 由 `server/media.mjs` 管理；`/api` 请求体上限 40MB。

## Goals / Non-Goals

**Goals:**

- 一个 7.4MB 的真实资料包能在一次上传后变成「可逐项确认的导入计划」。
- 解包在服务端完成且边界清晰：危险条目被拒、超限被中止、临时文件必被清理。
- 分类结果可解释、可改判；有歧义时不猜。
- 每个文件最终都走已存在的解析/上传路径，不产生第二套逻辑。

**Non-Goals:**

- `.rar` / `.7z` / 加密 / 分卷（Node 无内置支持，需要系统命令或原生依赖）。
- 目录结构推断项目名、自动建项目、自动合并成一次「全项目导入」。
- 从 Git URL 直接拉取（用户可以把仓库下载成 zip）。
- 解包后的文件在服务端长期保存或可再次访问。

## Decisions

### 决策 1：自己解析 ZIP，不新增依赖、不调系统命令

ZIP 格式的必要子集很短：读 EOCD → 读中央目录 → 按本地头偏移取数据 → `inflateRawSync` 或直取。

替代方案 A：加 `adm-zip` / `yauzl` 依赖。否决理由——仓库当前零解压依赖，为一个只需支持 stored + deflate 的场景引入包，还要在 Docker 与 Windows 上验证。

替代方案 B：调系统 `unzip`。否决理由——实测 Docker 镜像里没有这个命令；补装会给镜像加体积，且 `unzip` 对中文名的处理依赖 locale，反而不如自己控制解码顺序。

**代价**：需要自己处理 ZIP64、数据描述符（`flag & 0x8`）等边缘情况。范围限定：不支持 ZIP64（超过 4GB 的包直接拒绝，因为单文件上限本来就远小于此），数据描述符场景按中央目录声明的 `compressedSize` 读取（样本与主流工具都填写了）。

### 决策 2：解码顺序 UTF-8 → GB18030 → 安全名

```
flags & 0x800 置位  → 按 UTF-8 解码（规范行为）
未置位             → 先试 UTF-8（macOS 的行为），失败再试 GB18030（覆盖 GBK）
两次都失败          → safeName（hex + 原扩展名），清单里标注原名不可读
```

「UTF-8 失败」的判定用 `TextDecoder('utf-8', { fatal: true })` 抛错，而不是解码出替换字符——后者会把 GBK 的中文静默变成一堆 `�`。

替代方案：直接按 `flags` 判断。否决理由——样本实测就是未置位但内容是 UTF-8；只看标志位会让所有 macOS 生成的包变成乱码。

### 决策 3：安全校验在写入之前，逐条判定

每个条目先过白名单式检查再落盘：

```
拒绝：绝对路径 / 含 .. 段 / 含盘符 / 反斜杠开头 / 符号链接或设备（unix mode 的 S_IFLNK、S_IFCHR 等）
忽略：__MACOSX/ 前缀、.DS_Store、._*（AppleDouble）
拒绝：内层 .zip/.rar/.7z（作为「不可导入」列出，不解包）
```

用 `unixMode = externalAttrs >>> 16` 判定文件类型，这是 ZIP 规范里跨平台携带 unix 权限字段的位置。不是所有生成器都填这个字段（填 0 时按普通文件处理）。

### 决策 4：三层限额，任一项触发即整体中止

| 限额 | 建议值 | 理由 |
|---|---|---|
| 条目数 | 2000 | 真实资料包 31 条；2000 足够，且能挡住「几万个小文件」的耗尽攻击 |
| 单文件解压后 | 30MB（图片）/ 2MB（文本） | 与 `MAX_REF_BYTES` 一致；文本 2MB 远超任何剧本 |
| 解压后总计 | 300MB | 样本 7.8MB；给多集项目留足空间，同时低于临时目录的常见配额 |

**不按压缩比判定**——样本实测 1.01，真实素材包普遍接近 1，按 ratio 会误杀。改用「解压字节数达到声明上限即中止」：解压时累计已写字节，超过声明上限立刻停并删除已写文件。这样即使中央目录谎报大小，膨胀也会在超限时被打断。

### 决策 5：分类器输出「用途集合」，不是单一类别

实测样本推翻了「一个文件一种类别」的假设：

- `第01集_我差点没活过那个雨夜.md` 标题写「完整剧本」，但内含 `## 逐镜头分镜表` 与 `## 完整旁白稿`。它同时是剧本和分镜表。
- `第01集/02_前10集分集大纲.md` 放在 `第01集/` 目录里，但内容是 10 集的大纲。按目录推断会把它写成第 1 集剧本。

所以签名是 `classifyFile({ path, textPreview }) → { labels: Label[], episodeScope: 'single' | 'multi' | 'none', episodeNo?, confidence, reason }`。

```
label ∈ { script, shotlist, prompts, characters, image }
空集合 → 待判断（UI 显示「让模型分析」）
```

用实测样本校准的规则：

| 依据 | 规则 | 样本命中 |
|---|---|---|
| 路径 | 目录名含「参考照片」「图片」「参考图」→ image | `猫咪真实参考照片/*.jpg`（9 张） |
| 文件名 | 含「角色档案」「项目设定」→ characters | `01_项目设定与角色档案.md` |
| 文件名 | 含「分镜」→ shotlist | `03_第1集完整剧本与分镜.md` |
| 文件名 | 含「提示词」→ prompts | `05_AI镜头生成提示词.md` |
| 内容 | 表头行**首列**为「镜头」或 `shot` → shotlist | 两份第 1 集分镜表 + 第 2~10 集 |
| 内容 | 含 `**Prompt**` 或 `Negative prompt` → prompts | 提示词文档 |
| 内容 | 含 `### 外观锚点` 或 `## 角色A：` → characters | 角色档案 |
| 内容 | 含 `# 第N集` 或 `故事梗概` → script | 10 个分集文件 + `03_…分镜.md` |
| 都不满足 | → 空集合，待判断 | `04_真实拍摄清单.md`、`06_剪辑与发布规范.md`、两个 README |

**两条被实测证伪的规则**（原设计写错了）：

1. **「内容含『镜头』二字就是分镜表」→ 错。** `猫咪真实参考照片/README.md` 的表格单元格里写着「走路镜头」「转场空镜」，按关键词会误判成 12 镜的分镜表。必须锚定表头首列。
2. **「一个文件一个类别」→ 错。** 10 个分集文件全是「剧本 + 内嵌分镜表」双用途。

### 决策 5b：集号范围由内容决定，不由目录决定

`episodeScope` 按内容里的 `## 第 N 集` 小节数判定：

- 0 个 → `none`（如角色档案、提示词文档，本来就不属于某一集）
- 1 个 → `single`，取该集号
- ≥2 个 → `multi`（多集大纲），必须由用户决定拆分方式或排除

文件名里的 `第(\d+)集` 只作为**辅助校验**：与内容判定冲突时以内容为准，并在预览里标注「文件在 第01集/ 目录但内容是第 5 集」。

**代价**：`multi` 的文件没有自动拆分路径——因为大纲的 `###` 结构（情绪/实拍/AI 三行）与剧本的 `## 场次` 结构不同，无法可靠映射到 `script-v1`。本期要求用户手动处理或排除。

### 决策 6：冲突检测按「用途 + 集号」聚合

```
groupKey = `${kind}:${episodeNo}`
同 groupKey 下 ≥2 个候选项 → 冲突
```

样本里的真实冲突：`第01集_我差点没活过那个雨夜.md`（10 镜，区间形式 `00-05`）与 `第01集/03_第1集完整剧本与分镜.md`（12 镜，`0–5秒` 形式）都是第 1 集的分镜表，镜数不同。不合并——两份是不同阶段的版本，合并会产生 22 个镜头的怪物。

**集号抽取**：从内容里的 `## 第(\d+)集` 小节取，文件名的 `第(\d+)集` 只作校验。取不到集号的剧本类文件 → 冲突检测跳过，但在预览里标注「无法确定集号，将按导入内容里的集号写入」。

样本里的真实冲突：`第01集_我差点没活过那个雨夜.md`（10 镜，区间形式 `00-05`）与 `第01集/03_第1集完整剧本与分镜.md`（12 镜，`0–5秒` 形式）都是第 1 集的分镜表，镜数不同。不合并——两份是不同阶段的版本，合并会产生 22 个镜头的怪物。

### 决策 7：服务端只负责解包与列清单，不做分类

`POST /api/import/bundle` 返回 `{ files: [{ id, path, name, size, kind: 'text'|'image', textPreview? }], rejected: [...], warnings: [...] }`。

分类放前端，因为：改判是纯前端交互；分类规则会随真实输入快速演进，放前端改一次就生效，不必重启服务；模型分析本来就走前端已有的 `callText`。

**代价**：`textPreview` 需要把文本文件内容带回前端（截断到 4000 字符），一次 10 个文件约 40KB，可接受。

### 决策 8：临时目录用 `os.tmpdir()` + 随机名，请求内清理

解包写入 `os.tmpdir()/bundle-<random>/`，随响应结束（`res.on('close')`）删除。预览阶段前端持有的是「清单 + 文本预览」，不需要再取文件；用户确认导入时前端把**文本内容**随请求传回，图片则按 id 再从临时目录读一次。

这里有个矛盾：清理得太早，用户确认时读不到图片；太晚，临时文件长期堆积。选择：**响应时保留临时目录，在「确认导入」请求里带上 bundleId，导入完成后立即删除**；同时设一个 10 分钟的空闲回收（进程内定时器），避免用户关页面导致残留。

替代方案：把图片 base64 一次性全带回前端。否决理由——9 张图共 7.4MB，base64 后 10MB 塞进响应，且前端还要再传回来。

### 决策 9：整套导入是一次事务性的预览

预览里把所有文件的结果合成一份计划：

```
[剧本] 第01集_….md      → 第1集，1 集 5 场        新增
[分镜] 03_…分镜.md      → E01，12 镜              ⚠ 与另一份冲突
[提示词] 05_…提示词.md   → E01，0 镜（无镜号列）    ⚠ 需要镜头先存在
[角色] 01_…角色档案.md   → 3 个角色               新增
[参考图] 9 张            → 9 张图片                新增
[排除] 04_拍摄清单.md、06_剪辑规范.md
```

用户逐组确认后一次性应用。任一组失败则整次回滚（图片已落盘的保留并说明，因为文件写入不可逆，但项目数据不写入）。

## Risks / Trade-offs

- **自己写 ZIP 解析器** → 只支持 stored + deflate + 非 ZIP64；遇到不支持的包明确报错而不是产出坏文件。用真实样本 + 构造的恶意包做双向验收。
- **临时目录残留** → 10 分钟空闲回收 + `res.on('close')` 双重清理；残留目录名带前缀便于巡检脚本识别。
- **分类器误判** → 每条分类都带 `reason` 与 `confidence`，预览可改判；`none` 一律不自动导入。
- **两份分镜表可能是同一份的重排** → 不自动 diff 内容，只报镜数差异让人判断；后续可加「按镜号比对」。
- **图片必须先落盘才能预览** → 临时目录里的图片通过一个新路由按 bundleId + 安全名读取，且该路由只允许读临时目录内的文件。
- **7.4MB 的包上传走 JSON base64 会膨胀到 10MB** → 仍在 40MB 请求体上限内；但为将来留余量，改用 `application/octet-stream` 直传二进制，文件名走 header（与 `/api/deliverables/import` 一致）。

## Migration Plan

无数据迁移、无表结构变更。

回滚：撤掉 `/api/import/bundle` 路由与压缩包入口即可；已导入的项目数据与文件不受影响。
