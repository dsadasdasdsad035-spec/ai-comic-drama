# Design

## Context

导出的数据源与画布是两回事：`App` 里 `projectShots` 持有整个项目的镜头记录（`ProjectShot[]`），`episodes` 持有分集元数据（标题、钩子、目标时长、场次）。而画布节点 `ShotData` 是当前集的展示态，且不含 `desc`——`shotSync.ts` 的 `nodeToData` / `nodeToShot` 双向映射里都没有这个字段，画面描述只存在于项目文件。

导入侧的 Markdown 契约已经由几处代码钉死，导出必须反向满足它们：

- `intake/classify.ts:hasShotTable` 要求表头行首列是 `镜头` / `shot` / `镜号`。
- `intake/classify.ts:episodeScopeOf` 用 `^#{1,6}\s*第\s*(\d+)\s*集` 在全文件计数，`0` 或 `2+` 都会脱离「单集」。
- `intake/rows.ts:rowsFromTable` 只取「第一个表头能映射出镜号」的表格块，多张表会被丢掉。
- `intake/tableMap.ts` 的别名表决定哪些表头能被识别。
- `intake/BundleDialog.tsx` 只处理 `episodeScope === 'single'` 的分镜表，多集的会跳过写入。
- `shotSync.ts:SHOT_IMPORT_FIELDS` 是导入可写字段白名单，产线产物不在其中。

打包能力也已有现成实现：`src/creative/expertExport.ts` 用 `fflate` 的 `zipSync` 生成 zip 再以 Blob 下载，无需服务端参与。

## Goals / Non-Goals

**Goals:**

- 导出结果既是可交付文档，也是能被现有压缩包导入路径原样写回的项目快照。
- 渲染是纯函数，不依赖 React、不依赖画布状态，可在 Node 下用 esbuild 打包后直接断言。
- 导出与导入共用一份字段契约，避免出现第二套列名或第二种台词写法。

**Non-Goals:**

- 不做服务端导出接口、不写 `exports/` 目录（那里是成片产物的共享池，按项目生命周期不随项目删除）。
- 不做「导出后在应用内编辑再回写」的表格界面。
- 不导出媒体清单与相对路径（离开项目目录即失效）。
- 不改动分集剧本（script-v1）的导出格式；集数与场次的回灌仍走既有剧本导入路径。

## Decisions

**1. 渲染源用 `projectShots` + `episodes`，不用画布节点。**
备选是从 `nodes` 渲染（现有 `exportJson` 的做法）。否决理由：节点缺 `desc`，且只含当前集；节点还带坐标与标注，属于工程态。用项目数据还顺带解决了「标题硬编码成另一个项目名」的问题。

**2. 一集一个文件；全部集打包 zip。**
备选是单文件多集，或额外生成 `index.md`。否决理由分别是：多集文件被 `episodeScopeOf` 判成 `multi`，`BundleDialog` 直接跳过写入；`index.md` 这类说明文件在压缩包导入里会被列为「待判断」，每次回灌都多一次人工决策。
代价：全项目导出的产物是多个文件，只能靠 zip 交付——这正好复用了既有 zip 下载逻辑。

**3. 每份文件只有一张分镜表，场次作为列。**
备选是按场次拆多张表（更接近人工剧本排版）。否决理由：`rowsFromTable` 只认第一个带镜号的表块，其余场次会在回灌时丢失。加 `场次` 列既保住「一张表」，又让回灌能把镜头放回正确场次。

**4. 单元格转义用 `<br>` 与全角竖线，并在导入侧补 `<br>` 归一化。**
表格的一行就是一条记录，多行台词无法直接写入。备选：

- `\|` 转义：`markdownTableBlocks` 是按 `|` 直接切分、不做反转义，需要对导入侧做「转义 + 解转义」两处改动，且会影响用户手写文件里已有的 `\|`。
- 把多行台词压成 `A：x；B：y`：会丢失分段，且分号在文本里本就有语义。

选 `<br>` + 全角 `｜`：导出侧一次替换即可，导入侧只在 `splitDialogueCell` 入口加一条归一化，不改任何既有解析结果。

**5. 列集合固定为导入别名表里已存在的写法。**
列顺序为 `镜头 / 场次 / 时长 / 景别 / 运镜 / 画面与动作 / 台词与声音 / 首帧提示词 / 视频提示词`。时长写纯数字（`parseDuration` 直接接受），不写区间，避免导入侧做减法。景别与运镜写存量原值，不在此处做枚举归一。

**6. `desc` 与 `keyframe_prompt` 互不填充。**
很多项目只有首帧提示词、`desc` 为空。若为了表格观感把提示词抄进画面列，回灌时会把提示词写进画面描述，属于语义污染。宁可留空。

**7. 场次列在导入侧真正写入，而不只是统计。**
`rows.ts` 现在专门找场次列算 `scenesFallback`，但从没把值写进 `ImportShotRow`，`IntakeDialog` / `BundleDialog` 也都没透传，于是 `buildShotsFromModel` 永远回退到第一场——`workbench-text-intake` 里「预览列出回退到的场次」这条要求实际上无法兑现。改动是让已有字段真正被填上，`SHOT_IMPORT_FIELDS` 里本来就有 `scene_no` / `scene_slug`。

**8. 分集目录与画布各自触发，均非强调样式；删除顶栏「导出 JSON」。**
画布动作区已经有「导入 / 补齐锚点 / 插入」，导出追加在末位。顶栏按钮导出的是画布节点快照、标题写死，且违反 `workbench-shell` 的「视图专属工具留在视图内」，因此直接移除而不是保留。

**9. 文件名净化规则固定。**
`E{两位集号}-{标题}.md`；标题中的 `/ \ : * ? " < > |` 与连续空白替换为 `-`，去掉首尾连字符与点号；标题为空时退化为 `E01.md`。zip 名为 `{项目名}-分镜表.zip`，项目名同样净化。

## Risks / Trade-offs

- [存量景别/运镜不是枚举值（历史导入或模型写入）] → 导出写原文，回灌时 `normalizeSize` 会把无法归一化的词当「补充说明」并入画面描述。缓解：导出不改写数据；在验收测试里固定一条「枚举值原样往返」，非枚举值列为已知有损。
- [没有说话人前缀的台词行回灌后会落到画面描述] → `splitDialogueCell` 把无前缀段落判为声音说明，`rows.ts` 再把它并入 `desc`。缓解：文本不丢失，只是换了字段；这类行在存量数据里占比很低（`parseDialogue` 对无冒号行才产生空说话人）。
- [用户手里同时有手写分镜表和导出的 md] → 压缩包导入会报同集冲突并要求二选一。这是既有正确行为，不额外处理。
- [移除顶栏「导出 JSON」影响依赖节点快照的使用者] → 该文件含画布坐标与标注，从来不是项目数据的可回灌副本。需要读项目数据时走既有读工具或「导出全部」。回滚策略：恢复按钮即可，无数据迁移。
- [超长提示词让单元格极宽] → Markdown 表格不折行也不截断，这是「不丢内容」的代价；需要阅读体验时可交给外部渲染器处理。

## Migration Plan

无数据迁移。导出为纯新增能力；除删除一个顶栏按钮外不改变既有界面行为。导入侧的 `<br>` 归一化与场次写入只影响未来的导入操作，已保存的项目文件不会被改写。

## Open Questions

- 是否需要「复制 Markdown 到剪贴板」入口，取决于用户是否更常把内容粘进外部对话而不是存盘；可在此变更外单独评估。
